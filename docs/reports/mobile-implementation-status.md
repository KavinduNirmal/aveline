## Answer first

**The mobile app is mostly honest about what it does — and the three places where it is not are the
most important findings in this report.**

The honesty convention is real and deliberate, and the reviewer should preserve it while fixing what
follows. There are no empty callbacks, no `onPressed: null` placeholders and no inert buttons in
`lib/` (`grep -rn "onPressed: () {}" lib` matches nothing), and an action whose slice is not built
normally says so out loud — "Clock-in is not on mobile yet." (`quick_actions_row.dart:13`),
"Mentioning a piece to Aveline is not available yet." (`catalog_product_screen.dart:201`),
"Recorded on this screen. The concierge is not updated yet." (`customer_screen.dart:1610`). That
convention holds everywhere except the controls in finding 1, which is what makes them stand out.

**Four findings, ordered by how much damage they do.**

1. **Three controls report an outcome the app did not produce.** These are worse than a missing
   feature, because a missing feature is visibly missing while these read as done (§5.1 lists them
   plus a fourth silent no-op). The Blossom meter's "Request additional blossoms" toasts *"Request
   sent to the owner for approval."* while sending nothing (`blossom_usage_card.dart:221-223`) — the
   code's own comment admits "the request action is UI only" (`:18-20`). The Salon confirms an
   optimistic message as sent whenever it has no live conversation (`salon_screen.dart:396-402`).
   The header's search button opens a box whose input is wired to nothing
   (`search_overlay.dart:71`, `aveline_header.dart:57`).
2. **The client book and the client profile are 100 % demo, and they are wired into production.**
   `app.dart:350` injects `DemoCustomerRepository()` as the app's one `CustomerRepository`. Every one
   of the 38 clients the associate sees is a literal in `demo_customer_repository.dart:400-757`, and
   every preference, memory, occasion, interaction and consent row on the profile is generated by
   `math.Random` seeded from the client's id (`demo_customer_repository.dart:108-131`). The backend
   now serves a real tenant customer surface (`CustomerTenantEndpoints.cs:25-219`, eight org-scoped
   routes) and the mobile app calls three of them — all three from Home, not from the Customers tab.
3. **Catalog item creation and management do not exist on mobile in any form.** There is no create
   screen, no edit screen, no delete affordance, and no import. `CatalogProductRepository` has four
   operations and none of them writes a new piece (`catalog_product_repository.dart:40-72`). Of the
   **30** routes `CatalogEndpoints.cs` maps, mobile calls **4**. The route
   `POST /api/v1/orgs/{id}/catalog/items` has no mobile caller, and `Permissions.catalogManage` is
   declared, granted to four roles, and referenced by no screen.
4. **Two flows are actively broken in production**, not merely absent: Home's "Log a visit" and both
   of the app's links into a client profile. They pair an API-backed reader with the demo-backed
   writer, so the write is rejected or the profile resolves to nothing.

The commerce slice (order taking, payments, deliveries, approvals, business rules) is the largest
wholly-absent area, but it is honestly absent rather than falsely present — see §4.6.

**Confidence:** `Confirmed` for every item above and for every `file:line` in this report; each is a
direct read. `Inferred` is used only where marked, for runtime consequences that follow from the
code but were not observed by running it. One item is `Unverified` and is labelled in §9.

## 3 · Customers — the focus area

### 3.1 The book renders fiction, and it is the production path

`Confirmed.` `app.dart:350` is the whole finding:

```dart
_customerRepository = DemoCustomerRepository();
```

That single instance is handed to both the book (`app.dart:718`) and the profile (`app.dart:733`).
`DemoCustomerRepository`'s doc comment states its own status — "Stands in for the customer lookup
until the concierge slice is wired" (`demo_customer_repository.dart:9-11`). The 38 clients are
literals at `demo_customer_repository.dart:400-757` with ids of the form `CUS-1001`
(`demo_customer_repository.dart:401`), and each profile's preferences, memories, occasions and
interactions are generated per-client from `math.Random(customer.id.hashCode)`
(`demo_customer_repository.dart:110-131`). The book is pinned to a fixed clock —
`_reference = DateTime.utc(2026, 9, 17)` (`demo_customer_repository.dart:104`) — so "last visit
4 days ago" is a constant, not a fact.

### 3.2 The API surface exists, and mobile reaches almost none of it

`Confirmed.` The tenant surface was added after the mobile screens were last wired. Its eight routes,
all under `BoutiqueCustomerAccessPolicy`:

| Route | Mobile implementation | Production caller | State |
|---|---|---|---|
| `GET /orgs/{id}/customers/highlights` | `api_customer_tenant_repository.dart:47-71` | `api_home_repository.dart:40` | **Wired** |
| `GET /orgs/{id}/customers` | `api_customer_tenant_repository.dart:25-44` | none | Written, never called |
| `POST /orgs/{id}/customers` | `api_customer_tenant_repository.dart:74-104` | `api_home_repository.dart:64-66` | **Wired** (Home walk-in) |
| `POST /orgs/{id}/customers/{cid}/interactions` | `api_customer_tenant_repository.dart:108-122` | `api_home_repository.dart:69-71` | **Wired** (Home log-visit) |
| `GET /orgs/{id}/customers/{cid}` | — | — | Not implemented |
| `GET /orgs/{id}/customers/{cid}/interactions` | — | — | Not implemented |
| `PATCH /orgs/{id}/customers/{cid}` | — | — | Not implemented |
| `DELETE /orgs/{id}/customers/{cid}` | — | — | Not implemented |

`fetchBook` is the sharpest case: a complete, tested HTTP implementation of the exact call the
Customers tab needs (`api_customer_tenant_repository.dart:25-44`; tests at
`test/features/customers/api_customer_repository_test.dart:71-105`) that no production code path
reaches. The tab cannot use it today anyway — `CustomerQuery` carries `search` and `level`
(`customer_repository.dart:6-17`) and the endpoint accepts both
(`CustomerTenantEndpoints.cs:44-56`), but `ApiCustomerTenantRepository` lives in the `home` feature
and is not exposed to `customers`.

### 3.3 The client profile shows four sections no tenant route can serve

`Confirmed` for the field inventory; `Inferred` for the consequence.

The profile renders preferences, memories, occasions, interactions and consent
(`customer_screen.dart:24-37`, `:688-713`, and the four `_EmptyNote`s at `:1088`, `:1204`, `:1241`,
`:1357`). The tenant detail DTO is:

```csharp
public sealed record TenantCustomerDetailDto(
    Guid CustomerId, string? FullName, string? Nickname, string? PhoneNumber, string? Email,
    string? Level, string Status, decimal TotalSpent, int VisitCount, DateTime? LastVisitAtUtc,
    int LoyaltyTierIsDerived, DateTime CreatedAtUtc, DateTime? UpdatedAtUtc,
    int InteractionCount, IReadOnlyList<string> Tags);
```

(`CustomerTenantDtos.cs:97-113`.) No preferences, no memories, no events, no consent. Those live
only under `/internal/customers/**` (`CustomerConciergeEndpoints.cs:20-22`), which is bound to
`InternalServicePolicy` and an `X-Internal-Token` shared secret, and is documented as "Not callable
by frontends" (`docs/api/README.md:662`).

**Consequence (`Inferred`, but the API's own remarks say so):** re-pointing the profile at
`GET /orgs/{id}/customers/{cid}` is not a one-line swap. Five of the page's sections would have to
be dropped or the tenant surface extended. The API states the boundary as intentional — the detail
DTO is "Deliberately **not** the internal customer shape: no memory, no extracted AI context and no
internal-token fields reach a staff device" (`CustomerTenantDtos.cs:91-94`).

### 3.4 The profile's two actions are local-only, and it admits it

`Confirmed.` `_logVisit` builds a `CustomerInteraction` with id `local-visit-<micros>` and bumps
`visitCount` in local state (`customer_screen.dart:143-168`); `_recomputeStatus` recomputes the tier
client-side (`customer_screen.dart:174-192`). The screen prints the truth under them: "Recorded on
this screen. The concierge is not updated yet." (`customer_screen.dart:1609-1616`).

This is the one place where the same action is wired on one screen and not another: Home's "Log a
visit" calls the API (`home_screen.dart:325-348`), while the profile's "Log a visit" writes to a
local list. Backed by `POST /{cid}/interactions` (`CustomerTenantEndpoints.cs:100`), which the
profile does not call.

### 3.5 Two production flows are broken, not absent

`Confirmed` for the code paths; `Inferred` for the resulting 404, which follows from the `:guid`
route constraint and was not observed by running the app.

**a. Home's "Log a visit" writes a demo id to the live API.** `HomeScreen` is mounted as
`const HomeScreen()` (`main_shell.dart:29`, `staff_screens.dart:22`) and its `customerRepository`
parameter is never supplied, so the picker falls back to `DemoCustomerRepository()`
(`home_screen.dart:294`). The picked id is then `CUS-1001`-style. The write goes to
`POST /api/v1/orgs/{id}/customers/{customerId:guid}/interactions`
(`api_customer_tenant_repository.dart:108-122`) against a route constrained to a GUID
(`CustomerTenantEndpoints.cs:100`). A non-GUID segment cannot match, so the request fails.

The screen handles this correctly — `HomeController.recordVisit` reports the refusal and the screen
toasts "The visit could not be logged." (`home_controller.dart:176-185`, `home_screen.dart:337-344`)
— so the user is not deceived. The flow simply cannot succeed for any client the picker can offer.

**b. Both links into a profile lead to "Client not found".** Home's client row is API-backed
(`api_home_repository.dart:40`) and its tiles push `AppRoutes.customer(client.id)` with the API's
real GUID (`client_link_section.dart:89`). The Messages inbox is API-backed and does the same
(`conversations_screen.dart:238`). Both land on `CustomerScreen`, which resolves through the demo
repository (`customer_screen.dart:61-62`) and renders "Client not found"
(`customer_screen.dart:253`). A real client's notification or message therefore opens onto nothing.

### 3.6 The create and manage half of the client book

`Confirmed.` The "New customer" button is a floating action at `customers_screen.dart:340-348`
whose handler is a toast: "New clients are added from Home's walk-in slot for now."
(`customers_screen.dart:213-218`). The comment above it is explicit that this is a single seam
waiting for a form (`customers_screen.dart:207-212`). The only working path to create a client is
Home's walk-in sheet (`quick_add_client_sheet.dart` → `home_controller.dart:162-170` →
`POST /customers`), which collects a name and nothing else.

There is no edit screen, no delete affordance, and no way to reach `PATCH`/`DELETE`.

**A permission gap sits under this.** The backend defines `customers:manage`
(`Aveline.Api/Authorization/Permissions.cs:33`), grants it to the manager/supervisor/owner roles
(`Permissions.cs:196,200,204`), and gates both write routes with it
(`AuthorizationConfiguration.cs:272-275`; `CustomerTenantEndpoints.cs:186,217`). The mobile
permission map has no such constant — `lib/core/auth/permissions.dart:5-70` lists 24 permissions and
`customers:manage` is not among them, and `grep -rn "customers:manage" lib` matches nothing. A
client-side write UI could not be gated on the grant the server enforces without adding it first.

(`lib/features/catalog/presentation/screens/`: `catalog_screen.dart`, `catalog_filter_screen.dart`,

The grid's own structure confirms the absence: search field, filter button, tag row, grid

### 4.3 The taxonomy the catalog displays is placeholder data

`Confirmed.` The tag row is fed by `demoCatalogTags()` (`catalog_screen.dart:208`), a hardcoded
list of ten tags (`demo_catalog_tags.dart:8-19`) whose own doc comment says it is a "Placeholder
stand-in for the tags a boutique defines for its own catalog". The filter options are a `const` enum
(`catalog_filters.dart:6-53`) headed by "The options are placeholders until the boutique's own
inventory taxonomy is wired" (`catalog_filters.dart:3-5`).

Both are half-connected: the chosen tag ids and filter values *are* sent to the API
(`api_catalog_product_repository.dart:140-187`), so the narrowing is real while the vocabulary
offered is invented. `GET /facets`, which exists to supply it, is unused (`CatalogEndpoints.cs:113`).

### 4.4 One action is deliberately fake, and says so

`Confirmed.` "Mention to Aveline" (`catalog_product_screen.dart:408-419`) calls
`_mentionToAveline`, which toasts an error and deliberately does **not** flip its own state flag:

```dart
// Deliberately not a state flip. … Saying she was told would be the screen lying about
// what it did, which is the whole reason the other four actions are wired.
AppToast.show(context, 'Mentioning a piece to Aveline is not available yet.', error: true);
```

(`catalog_product_screen.dart:189-204`.) There is no backing endpoint — no route in `Aveline.Api`
accepts a piece-to-agent mention. This is the honest-unimplemented pattern, not a defect.

The other four actions are wired: three status transitions through `_applyStatus` →
`PATCH /items/{id}/status` (`catalog_product_screen.dart:121-151, 358-395`) and
`_requestSupply` → `POST /catalog/sourcing` (`:157-187`).

### 4.5 The demo catalog repository is still a live fallback

`Confirmed.` `DemoCatalogProductRepository` no longer reaches production — the router injects
`_catalogRepository` (`app.dart:677,711`) — but it remains the default in both screens
(`catalog_screen.dart:82`, `catalog_product_screen.dart:44`). Any future mount that omits the
parameter serves 8 in-memory pieces instead of an error. The catalog's read path is otherwise
correct: with no organization id the API repository returns an empty page rather than fiction
(`api_catalog_product_repository.dart:24-26`), and a mutation with no organization id throws rather
than toasting a success (`:121-127`).

### 4.6 The inventory and commerce slices contain no Dart code

`Confirmed.` `find lib/features/inventory lib/features/commerce -type f` returns exactly two files:

```text
lib/features/commerce/README.md
lib/features/inventory/README.md
```

Both are forward-looking templates listing files that do not exist (e.g.
`inventory/README.md:8-12` names `inventory_api_client.dart`, `sourcing_api_client.dart`). There is
no inventory feature, and no commerce feature.

**Commerce is a mobile gap, not a backend gap.** An earlier draft of this report asserted the
opposite, because a sweep of `Aveline.Api/Endpoints/*.cs` finds no orders route. It is wrong: orders
are MVC controllers, registered by `app.MapControllers()` at `Program.cs:220` and therefore invisible
to a `Map*`-based search. Five controllers serve the commerce surface, 30 actions in total:

| Controller | Base route | Actions | Evidence |
|---|---|---|---|
| `OrdersController` | `/api/v1/orgs/{orgId}/orders` | 7 (list, get, create, update, status, cancel, recalculate) | `OrdersController.cs:30-145` |
| `PaymentsController` | `/api/v1/orgs/{orgId}/payments` | 6 | `PaymentsController.cs:12-120` |
| `DeliveriesController` | `/api/v1/orgs/{orgId}/deliveries` | 5 | `DeliveriesController.cs:10-84` |
| `ApprovalsController` | `/api/v1/orgs/{orgId}/approvals` | 6 | `ApprovalsController.cs:13-123` |
| `BusinessRulesController` | `/api/v1/orgs/{orgId}/business-rules` | 6 | `BusinessRulesController.cs:24-101` |

So `POST /api/v1/orgs/{orgId}/orders` exists and the mobile app calls none of it. The message "Order
taking is not on mobile yet." (`more_actions_sheet.dart:50`) is literally accurate. The whole
commerce slice — order taking, payments, deliveries, approvals, business rules — is unbuilt on
mobile against a live backend.

## 5 · False success, mock data, stubs and dead code

`Confirmed` unless marked. The section is ordered by severity, not by surface.

### 5.1 Actions that report an outcome the app did not produce

These are the findings that matter most: each renders as a completed action while nothing happened,
so the associate is misinformed rather than merely blocked.

| Control | What it claims | What it does | Evidence |
|---|---|---|---|
| Blossom meter — "Request additional blossoms" | "Request sent to the owner for approval." | Nothing. No request is built, no endpoint exists. The code's own comment: "The request action is UI only: it states what would happen and sends nothing." | `blossom_usage_card.dart:221-223`, comment `:18-20` |
| Salon composer | Message bubble settles into a confirmed (non-sending) state | When `organizationId`, `conversationId` or the API client is null, it confirms the optimistic bubble locally and returns. The comment calls this the "tests / not connected" path, but the same path is taken by any production session whose realtime connect failed (`salon_screen.dart:190-192` swallows that failure) | `salon_screen.dart:396-402`; swallow at `:190-192` |
| Header search | A search field that searches the shop | `SearchOverlay.show` constructs the overlay without `onQueryChanged` (`aveline_header.dart:57`), so the field's callback at `search_overlay.dart:71` is always null and there are no results — the body is static text (`:176`) | `search_overlay.dart:71,117,176` |
| Home — "Add client" on the client row | A new walk-in | When `onCreateWalkIn` is null the sheet still collects a name, then `return`s and discards it | `client_link_section.dart:66-75`; the null arrives from `home_screen.dart:273` (`controller?.createWalkIn`) |

The first three should be fixed before any feature work: a wrong success is the one output a reader
cannot detect. The fourth is a silent no-op rather than a false claim, and is cheap to fix by
disabling the tile.

### 5.2 The Salon's seeded thread is production state, not a fallback

`salon_screen.dart:39` initialises the message list from `_seedMessages()`, so four invented messages
(ids `m1`–`m4`, `salon_screen.dart:68-101`) are what the thread shows before the API answers. Worse,
a failed history fetch **appends a second copy** of the same seed rather than replacing it:

```dart
} catch (_) {
  if (mounted) setState(() => _messages.addAll(_seedMessages()));
}
```

(`salon_screen.dart:158-160`.) Because the seed is already the initial state, that path duplicates
four messages rather than filling an empty thread. The Salon is otherwise genuinely wired: real
conversation API, real history read and a live SignalR connection (`salon_screen.dart:120-190`).

## 9 · Risks and limitations

- **Nothing was executed.** No `flutter test`, no `flutter analyze`, no API call, no running app.
  Consequences marked `Inferred` (§3.3, §3.5) follow from the code but were not observed. In
  particular, the exact HTTP status produced by sending `CUS-1001` to a `:guid`-constrained route
  (404 versus 405) was not measured; only that it cannot match.
- **The web app was surveyed by its API-client tests and component filenames, not audited.** §6
  establishes that the web wires these endpoints; it does not claim the web UI is complete.
- **Route counts in §4.2 come from `CatalogEndpoints.cs` at this revision.** Two of the 30 are
  aliases (`POST /qr/scan` at `:465` duplicates the `POST /items/scan-qr` handler at `:455`), so
  "26 unwired" slightly overstates the distinct capability gap. The capability grouping in that
  table is the honest reading.
- **One item is `Unverified`:** whether the eight `POST /internal/customers/**` concierge routes and
  the three `/internal/visual/**` families are still consumed by `agnet-service/`. That does not
  affect any finding here — no mobile route depends on them — but it bears on whether the tenant
  customer surface should be extended (§3.3) rather than the internal one opened up.
- **Dead code and "unreachable" are static claims.** §5.3 and §5.4 were established by walking the
  import graph from `lib/main.dart` and by grepping for each symbol, not by running the app. A screen
  reached only through a runtime-constructed route name or a deep link I did not find would be
  mislabelled dead. The routes I could check are enumerated in `app.dart:667-832`, and no registered
  route points at any file listed in §5.4.
- **The mobile working tree is clean, the backend working tree is not.** Findings on the API side
  describe the backend **as checked out**, which includes uncommitted changes to
  `Aveline.Api/Modules/Commerce/**` and elsewhere. None of those files are cited above.
